## Review and resolution

A bracketed destination remains exact source text, attached to its stable source allocation. Parsing neither chooses an account nor creates a movement. The Transfers dialog shows each allocation's amount, source destination and identity. The destination selector starts with an unselected placeholder; account labels include name, currency and stable identity to distinguish duplicate names. Outside the complete mapped-export exception below, names are never matched automatically or normalized. An old export name can be explicitly mapped to a differently named account. Create missing accounts through the existing account workflow first.

For an unresolved allocation, explicitly choose the destination account and use **Use as transfer**, or select the existing transfer and **Match selected allocation** after reviewing its counterpart. The category selector also lists real accounts. Choosing one stores that account identity and uses the same generation or replacement command. It does not search for an existing independent row, and a category with the same name does not create a transfer. Renaming the account leaves the stored identity in place. Bracketed source text still opens the Transfers dialog when the user is resolving that source label. Creation, matching, Merge, and replacement use complete atomic commands and durable operation receipts. Matching remains provisional until that importing account commits. Equal amounts alone do not authorize a match. Repeated equal allocations retain distinct identities and must be resolved separately. Cross-currency, self-account and nonexistent destinations are rejected.

Included bracketed allocations cannot commit without a live origin link or a provisional/attached evidence link. Partial resolution of a split does not satisfy this check. Storage enforces it independently of the UI and checks committed relationships again on authenticated open. Explicit ordinary duplicate review remains available; excluded duplicates do not create a second transfer. Drafts and unresolved source names survive restart.

Ordinary editing cannot delete an imported transfer allocation, replace its bracketed destination with a spending category, or invent a bracketed destination on an unrelated allocation. Use transfer commands for account assignment. Before linking, rules may update descriptive fields and ordinary fee categories, but preserve transfer destinations even when replacing manual values; previews explain that protection. Source bytes, allocation associations, money and rule provenance remain independently validated. Financial corrections before linking retain the existing exact-money validation; linked edits remain guarded by the existing repair/reversal boundary.

Per-account commit, draft protection, discard, later evidence attachment, independent posting dates and counterpart navigation retain the existing [transfer contract](transfer-engine.md). Neither resolution nor matching commits the opposite account. Source-first and destination-first imports use the same explicit workflow.

## Limits and verification

Only the existing banking dialect is extended. Multi-account QIF sections, investment records and category/class suffixes remain unsupported. Empty, nested, unbalanced or class-suffixed brackets fail explicitly. Account-name alias persistence, committed transfer reversal, and cross-currency conversion remain outside this package. Merge, unlink, replacement, linking two independently committed equal allocations, account entries in the category selector, and the read-only transfer journal are implemented; see [transfer management](../features/008-transfer-matching-and-lifecycle.md#accepted-transfer-management-decisions--2026-10-27). Grouped evidence links only at the equal allocation, not at the transaction total. This does not claim general QIF compatibility or complete feature 008.

Synthetic tests cover parsing, malformed notation, rules protection, both import orders, unknown/duplicate names, explicit identity choice, unresolved/partially resolved commit rejection, repeated equal allocations, mixed signs, reopen, backup restoration and UI resolution. Existing transfer write/sync and interruption sweeps now use bracketed source and bank fixtures. Actual configuration results are recorded in [project status](status.md#qif-transfer-destinations--2026-10-26).

## Complete named-account export exception — 2026-10-28

The owner superseded repeated manual destination selection for a complete export whose source accounts have already been explicitly mapped. The [confirmed-mapping resolution](qif-account-imports.md#reusing-confirmed-mappings-for-transfer-pairs--accepted-2026-10-28) automatically links mutual unique, same-date, same-currency reciprocal allocations without creating money or duplicate records. Remaining cases stay visible as navigable blockers. This is narrower than general automatic statement matching; standalone imports, different-date candidates, ambiguous pairs and cross-currency conversion are not silently resolved. Current schema-30/29 drafts can use the new command without reimport.
