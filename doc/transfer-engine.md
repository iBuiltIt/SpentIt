# Transfer lifecycle engine and durable workflow

Last updated: 2026-10-26

The bounded same-currency [transfer lifecycle](../features/008-transfer-matching-and-lifecycle.md) now connects the pure engine to encrypted storage and the durable import UI. Rules-enabled documents use experimental schema 10; rules-off documents use schema 11. Older experimental formats are rejected without migration. QIF account-destination syntax remains rejected: this package creates manual transfer drafts or assigns an already valid imported allocation through the Transfers dialog. Full feature 008 remains active.
## Implemented contract

`spentit::transfers` identifies each endpoint by account, entry and stable allocation identity. Generation selects an allocation by identity, including within mixed-sign splits or repeated equal payments. It creates an exact opposite amount in the same retained currency definition, using the origin date provisionally. Cross-currency inputs fail explicitly; negating the signed minimum fails with the existing checked-money overflow error. Generated provenance is distinct from independent bank evidence.

Pure commit proposals change only the explicitly selected account. The other draft becomes protected by the relationship to that committed side, in either commit order. Clearing a protected draft preserves it; clearing an ordinary imported origin removes its purely generated draft counterpart. Destination-only cancellation and removal involving independent evidence fail with explicit policy errors. These are conservative engine guards, not newly accepted product policies.

Complete-set validation rejects duplicate link identities, reused allocation endpoints, inconsistent states or dates of shared entries, conflicting account currency definitions and reuse of a generated entry. Whole-account proposal functions return all resulting links without mutating their input. When any allocation protects an origin entry, clearing its account preserves that entire entry and its sibling links. Persistence must supply the complete relationship set and perform revision checks and the complete storage transaction; the engine cannot establish completeness or durability on its own.

Match validation checks account, exact money and a valid independent posting date. Explicit proposals retain the evidence identity separately without changing the existing entry date, amount or commit state. Publishing a proposal changes only its account to committed and attaches the evidence; the opposite side keeps its prior state. Attaching evidence to an already committed entry leaves its amount unchanged. The engine does not suppress imported occurrences or calculate durable balance effects; storage performs the atomic integration described below. Candidate ranking, grouped evidence and repair remain unresolved.

The source files are `src/engine/include/spentit/transfer.hpp` and `src/engine/transfer.cpp`; tests are `tests/engine/transfer_tests.cpp`. They belong to the existing dependency-free engine target.

## Accepted evidence-matching and unmatched-entry policy

The owner accepted provisional matching: a confirmed match from a pending import remains a proposal until that importing account explicitly commits. Discarding that import drops the proposal and retains the original evidence, leaving the existing transfer's financial state and protection unchanged.

The owner clarified that manual and unmatched entries must be committable even when no bank record will ever arrive. Provide explicit acceptance as valid without a bank match, followed by separate account commit. Acceptance must preserve provenance and allow later matching. It does not override exact-money checks: −100 and +95 may each be committed as valid unmatched entries, but linking stays blocked until the difference is explicitly accounted for. See the [accepted decisions](../features/008-transfer-matching-and-lifecycle.md#accepted-matching-and-unmatched-commit-decisions--2026-10-26).

The engine now supports manual-origin generation, explicit unmatched acceptance, provisional evidence proposals, proposal discard and explicit publication. Unmatched manual/generated sides require acceptance before ordinary commit; acceptance alone changes neither state nor money and creates no bank evidence. Whole-entry acceptance applies consistently across sibling allocations. Creation provenance and the original generated date survive later matching, including when the bank posting date differs. Proposal publication requires the exact expected evidence snapshot. Whole-import helpers act only on the selected account and named import and reject reused bank allocations across links.

These transitions now have persisted commands, acceptance history, evidence retention, per-account financial publication and cancellation/recovery integration. Unresolved destination-only cancellation and committed repair/unlink/reversal still require explicit policy, and acceptance cannot bypass their safety invariants.

## Durable storage contract

`TransferRequest` carries an operation identity, exact expected financial sequence, stable link/allocation identities and, when applicable, the reviewed import revision. Commands create a manual pair, assign an imported draft allocation, accept an unmatched side, commit a local side, propose/drop a bank match, or clear an ordinary manual origin. Every command validates the complete relationship set. Exact retry returns the original receipt; changed content or stale previews fail explicitly. Ordinary editing/removal/Undo refuses linked entries until transfer-aware policies exist.

Encrypted immutable transfer events and version snapshots share the existing financial operation ordering. Heads select the current snapshot; authenticated open replays transitions, evidence identities/amounts/dates, local movement effects and retained-source membership. A match proposal leaves committed amounts unchanged. Projection counts the bank allocation once in place of its local generated/manual amount. Committing that import attaches evidence and removes the redundant local projection in the same SQLCipher transaction, without erasing the bank record. An already committed local side therefore produces a zero net balance change when equal bank evidence is published. Different posting dates survive, alongside original generated provenance.

Commit remains explicit per account. Imported origins commit through their batch; manual/generated entries commit individually after unmatched acceptance. Committing either side protects the opposite draft without committing it. Clearing an import retains any protected whole source row and its sibling links, excludes ordinary cleared rows, and permits another import. Retained rows have a separate explicit commit control. Dropping a pending bank import drops its proposal while preserving source evidence and the existing transfer. Complete operations and their history are one transaction; no UI loop owns a financial boundary.

## UI and bounded scope

The Transfers dialog exposes manual creation, assignment of a selected valid draft allocation to another account, exact-amount candidate review, explicit match proposals, unmatched acceptance, per-account commit, proposal removal and counterpart navigation. Candidate suggestions are bounded to 100 results and never auto-confirm. Generated dates and protected draft state are visible. Navigation restores each account's selection, filter, ordering and viewport within the current session; counterpart navigation reveals the destination and honors the unsaved-edit guard. Restart still begins in account 1.

The last operation receipt is visible; encrypted persistent transfer history is verified on reopen but does not yet have a dedicated browsable history screen. Existing ordinary committed-change history does not list transfer events. No transfer correction, unlink, reversal, fee resolution, automatic matching, cross-currency conversion or matching of two already independent committed entries is implemented. QIF `[Account]` admission/account-name resolution and a unified category/account picker remain follow-ups. Independently valid imported entries can still commit unmatched; acceptance does not authorize linking unequal amounts. No new responsiveness or native multi-platform claim is made.
