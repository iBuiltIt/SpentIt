# Experimental QIF profile v6

Last updated: 2026-11-10

Implementation contract for the accepted [durable import milestone](009-durable-import-milestone.md). This deliberately bounded profile is not general QIF compatibility. The field identifiers and transfer notation were checked against [GnuCash's QIF notes](https://raw.githubusercontent.com/Gnucash/gnucash/stable/gnucash/import-export/qif-imp/file-format.txt); restrictions below are SpentIt choices. No private export file was opened; the owner supplied a byte-level screenshot for the embedded-CR follow-up.

- UTF-8, optionally beginning with a BOM; LF or CRLF; embedded CR is accepted only in the free-text fields described below; no embedded NUL or other ASCII control characters except tab in text fields. Invalid encoding blocks the file. No decoding substitution.
- An optional initial `!Type:Bank`, `!Type:Cash` or `!Type:CCard` header selects ordinary monetary records. Headerless banking records support the synthetic Wise shape. Named account lists and repeated ordinary sections are handled by the account-section extension below; category catalogs are supported as described below; other headers remain unsupported. Blank lines are rejected. A final line need not end with a newline.
- A record ends with a line containing only `^`. Every record needs exactly one `D` date and `T` amount. Missing terminators, empty records and repeated singleton fields block the record. An empty file is an error.
- Dates accept unambiguous `YYYY-MM-DD`, or one/two-digit day and month separated by `/`, with a four-digit year in 0001–9999. The parser receives a DMY or MDY profile for slash dates; ISO dates ignore that choice. The import UI infers the profile across all transaction sections: dates valid in only one order establish that order. If valid dates establish conflicting orders, import is refused with an explicit correction message. When both orders remain possible and change a date, a dialog shows an actual ambiguous date and its two interpretations, with no preselection. Equivalent dates (such as `02/02/2026`) need no question. Invalid dates remain subject to ordinary parser diagnostics; account/category descriptions do not supply date-order evidence. Gregorian calendar validation rejects impossible dates. Normalized dates use YYYY-MM-DD without timezone conversion.
- Money uses exact ASCII decimal amounts and the supplied account currency definition. Comma thousands grouping is accepted only with one to three leading digits and exactly three digits per subsequent group, before a dot decimal separator. The same grammar applies to transaction totals, split amounts and reported account balances. No exponent, whitespace, locale guessing, rounding or inferred currency. Original imported totals are retained.
- Optional singleton `P`, `M`, `N`, `L`, `C` fields represent payee, memo, reference, category and cleared status. `C` supports empty, `*`, `c`, `X`, `R`; budget/reminder markers are blocked. Addresses (`A`, at most six lines) are evidence-only. Unknown fields, including `U` and percentage splits, block rather than override a total or silently lose semantics. Payee, memo, reference, category, and split-memo text read each `&amp;` as `&`. The same replacement applies to account names and descriptions, and to category names, descriptions, and tax-schedule text. Amounts, dates, cleared status, account type, and balances are left as written. A bare `&` stays, and `&amp;amp;` is read as `&amp;`. QIF export writes `&`.
- Splits repeat optional `S` category, optional `E` memo, in either order, then required `$` amount. Missing `S` supports Wise-shaped exports. A new group begins after `$`; repeated `S` or `E` within a group and incomplete groups block. Parent fields must precede split fields. Splits sum exactly to `T`; no balancing repair. Without splits, one allocation uses `L` and `M`. With splits, `L` must be empty or the literal `--Split--`; another parent category is ambiguous and blocked. Mixed-sign and zero splits are preserved.
- `L[Account]` and `S[Account]` retain explicit transfer destinations for [account resolution](../doc/qif-transfers.md). The bracket contents must be nonempty and not all spaces, with no nested brackets, tabs, newlines or class separators. Malformed brackets block. No account is inferred or created by parsing. One `/Class` suffix is accepted for an ordinary category or bracketed transfer destination. The nonempty class is retained separately as source metadata and displayed read-only; it does not create a category, account or report classification. Empty/space-only class names and class strings containing `/`, `|`, brackets or tabs are blocked. Investment `|` combinations remain unsupported. Ordinary category text is retained without a hierarchy model.
- Limits: 64 MiB source, 200,000 records, 1 MiB per record including terminator/newlines, 64 KiB field value, 1,000 allocations per record. Over-limit results are explicitly inadmissible for ingestion. One first diagnostic per record bounds error growth; file-level diagnostics stop parsing. Byte offsets, original-source line ranges and account-local record ordinals identify errors without putting financial values in messages.

A parse result does not commit anything. Source bytes remain the caller's immutable evidence; record byte ranges reference those exact bytes, including delimiters. Invalid records have diagnostics and no validated transaction. Valid records from an otherwise blocked file are never permission for partial commit. Application persistence and correction decisions are separate responsibilities.

The parser exposes an optional original amount, explicit source currency definition, and source-allocation fields whose amounts may be unavailable. Every syntactically complete split keeps its original position, category, memo and class even when `$` is invalid; no zero amount or shifted ordinal stands in for unknown evidence. Parsed allocations with known amounts are evidence only until exact transaction validation succeeds. A missing/invalid parent total still preserves the unsplit category/transfer destination.

Repairability requires intact record/split structure and only date, missing required date/total, exact-amount, or split-total errors. Unknown/repeated fields, encoding errors, malformed destinations and incomplete or ambiguous split grouping remain blocked. A repair must supply valid effective money and allocations, preserve transfer intent and source associations, and explicitly resolve duplicate disposition. Original unavailable money stays unavailable. Whole-import repair behavior is in [feature 003](003-qif-import-review.md) and [account imports](../doc/qif-account-imports.md).

## Account-section extension — 2026-10-26

The [whole-source account contract](../doc/qif-account-imports.md#accepted-source-envelope) specifies supported `!Account` lists, repeated ordinary sections, metadata fields, limits and refusal behavior. Each account's records reuse this ordinary grammar with explicit currency and date order. This does not admit investment or class-catalog sections, infer self-account opening records, or alter category/class and unknown-original repair invariants. See the [statement profile](003-ofx-profile.md) and [account commands](002-accounts-money-splits.md).

## Category catalog and literal slash names — accepted 2026-10-28

The owner approved complete catalog import for first-time transfers from another application, with starter categories disabled. `!Type:Cat` records accept `N` name, `D` description, `I`/`E` income/expense markers, `T` tax marker, `R` tax schedule and `B` budget text. Each record ends with `^`. Unknown/repeated fields, contradictory I/E markers, missing/invalid names and duplicate exact definitions are explicit errors. At most 4,096 category definitions are accepted. Empty or unused categories are not omitted. Metadata remains source evidence; it does not introduce income/expense category types, tax behavior or reporting exclusions.

A literal slash is allowed in editable category names. In QIF references the usual `/Class` syntax remains supported. An exact catalog-declared full name containing `/` is a literal name; a declared prefix can also precede a class suffix, including `Telephone/Cellular/Work` for declared category `Telephone/Cellular`. If both the full name and its category prefix are declared, interpretation is ambiguous and that record is blocked with a category/class diagnostic. There is no silent rename, slash replacement, class loss or fuzzy matching. Exports without a matching catalog definition retain conventional category/class parsing. Resolving such an ambiguous exporter dialect interactively remains outside this slice; the error requires a clarified source before reimport.

Catalog-only sources and catalogs followed by unnamed ordinary sections use one explicitly mapped target account. Named definitions and repeated account selections share the existing account workflow. Complete category staging, first-publication semantics, rollback and identity preservation are described in [the account-import contract](../doc/qif-account-imports.md#staged-category-catalog--2026-10-28).

The parser identity is `bank-v6`. The release rules database is version 1. A different number is refused, and the file bytes stay the same. There is no migrator.

## Embedded carriage returns — accepted 2026-10-28

LF and CRLF remain field-line separators. A lone CR inside ordinary payee (`P`), memo (`M`), reference (`N`), split memo (`E`) or evidence-only address (`A`) values is an embedded text line break. Account descriptions (`D`) and category descriptions/tax-schedule text (`D`/`R`) accept the same convention. Both interpreted strings and original source bytes retain the CR exactly; no global line-ending replacement, text deduplication or skipped continuation occurs. Text after that CR remains in the same value even if it begins with `T`, `!` or `^`.

Lone CR is still rejected in amounts, dates, names, category/class references, cleared status, headers and terminators. CR-only record delimiters are not supported. A trailing CR is stripped as a line ending only when followed by LF, never merely because it is the final byte. Existing field/record/file limits still include embedded text. Draft and committed review validation permit CR in payees and memos while retaining strict category validation. This does not implement a multiline editor.

Lone CR in those text fields is part of bank-v6. A file whose number is not 1 is refused, and its bytes stay the same. There is no migrator.

## Value-free structural diagnostics — accepted 2026-10-28

The owner approved a local diagnostic and clearer source locations after a large import reported only account-local record numbers and generic split errors. Diagnostic presentation now includes full-source LF-based line ranges, an error line and a specific split reason. A standalone read-only diagnostic shares the engine parser, suppresses values and paths, and reports bounded field-marker sequences and timings. No acceptance, repairability, publication or source-storage semantics change; no format bump is required. See [local usage and privacy boundaries](../doc/qif-diagnostics.md).

## Split field ordering — accepted 2026-10-28

The owner approved accepting either `S E $` or `E S $` after a value-free diagnostic report showed memo-before-category groups. Each group permits at most one category and one memo; `$` closes it. Both optional fields may still be absent. Repeated category/memo fields, incomplete groups, parent fields after splits, conflicting parent categories and non-balancing totals retain their existing rejection/repair behavior. Original bytes, field values, source allocation ordinals, classes and transfer destinations are preserved.

Either `S` then `E` or `E` then `S` is accepted in bank-v6. Reimport of an older experimental file uses a new file. Older files are refused unchanged.

## Conditional date-order prompt — accepted and implemented 2026-10-29

The ledger has no date-order selector. Import statement is available without a date choice, retaining existing busy/read-only/pending-import guards. OFX-family imports never prompt. The ambiguity dialog offers Continue after selecting Day / Month / Year or Month / Day / Year, and Cancel import. It retains the already-read source bytes in memory until confirmation or cancellation; confirmation does not reread a potentially changed file. No source is persisted while awaiting this choice. Dataset close/open/create clears the pending question. This changes import preparation only, not stored parser semantics or schemas.

The date-order dialog is part of the current import UI.
